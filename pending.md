- **Output and format**: the character set is its own folder, `packages/client/public/assets/characters/` (committed, about 0.6 MB optimized: `body.glb` 166 kB, most of it the 14 sampled clips; 16 `animal.<id>.glb` and 9 `outfit.<npc>.glb` of 8–25 kB each), with `character-manifest.json` (zod: `CharacterManifestSchema`). ## M16

- **Movement model (decision)**: clients predict their own walker with the shared `PlayerController` and report positions (`player:move` {seq, epoch, space, x, z, heading, motion}, ~20 Hz while moving, at once on stop/door/space change); the TownRoom validates every report with shared `world/moveValidation.ts` and corrects rejected ones (`move:correct` with a new epoch; reports from older epochs are ignored, so in-flight reports from a wrong path cause one correction, not a cascade). The old `player:input` (WASD dir / click target) message was removed: nothing used it, and the build plan asks for "server-side movement validation (speed caps, walkability)". Colyseus 0.18's built-in `Predict`/`defineInput` fixed-step reconciliation was considered and not used: it needs a fixed-step input simulation on both sides, which fits badly with the variable-frame click-to-move paths and the fade-gated door transitions; the validation model keeps the M13 controller as it is. Should it move to input-based simulation later (stronger anti-cheat, e.g. no "teleport within the speed budget")?
- **Validation rules (my numbers)**: a distance budget refills at run speed × 1.15 (4.83 m/s), capped at 1 s worth + 0.25 m (jittery reports bunch up); each accepted report spends its distance. The reported point must hold a walker (same rule as `moveWithCollisions`) and the straight segment must not cross blocked cells (0.05 m probe) unless a collision-sliding step lands within 0.2 m. Space changes only through a door of the current space whose trigger zone the last accepted point was within 0.6 m of, arriving within 0.75 m of the door's far side. A cheater can still move at ~4.8 m/s anywhere walkable; TODO(M36): count rejections toward a kick, rate-limit move/time-sync messages.
- **Spawn and sessions**: a joining player is placed in their apartment (`TOWN_SPAWN` = the apartment arrival point, as in M14); the welcome carries `{uid, shard, spawn}` and the client snaps there (a new session after a server restart therefore starts at home again; position is not durable). The client sends no reports until the welcome has arrived. A dropped connection keeps its seat for 20 s (`allowReconnection`). One session per uid: a newer session (another tab, any shard) closes the older one with close code 4801, and that client does not rejoin (HUD: "You are playing in another tab").
- **Private apartment**: the apartment interior is shared code but each player's own instance, so players there are never shown to others and emotes there are not relayed (`isPrivateSpace`). TODO(M17): the ApartmentRoom. Other interiors (bakery, café…) are shared spaces: players inside the same building see each other.
- **Shards**: `maxClients` 40; Colyseus locks a full room and `joinOrCreate` opens the next one; `sortBy({"metadata.shard": 1})` fills the lowest-numbered shard first. Shard numbers are the lowest free number (a disposed shard's number is reused). Join a friend: `GET /api/shards?friend=<uid>` (behind `requireAuth`) returns all shards and the friend's `{roomId, shard, clients, maxClients}` or null; the client then `joinById`s it and falls back to normal matchmaking when it is full or gone. Client entry point for now: the page URL `?friend=<uid>` (TODO(M37): a shard picker / friend UI). Privacy question: any signed-in player can look up which shard a uid is in (there is no friend list yet). Default: allowed; restrict to friends once a friend list exists.
- **World clock**: shared `world/clock.ts`: `phase = ((now − WORLD_EPOCH_MS) mod 40 min) / 40 min` with `WORLD_EPOCH_MS` = 2026-01-01T00:00Z (phase 0 = sunrise). My in-game mapping: sunrise 06:00, sunset 21:00 (30 real minutes of daylight = 15 in-game hours, 10 minutes of night = 9 hours); bands morning 06–12, afternoon 12–17, evening 17–21, night 21–06. The room state carries `world {serverTime (1 Hz), day, weather, previousWeather, weatherSince}`; clients sync their clock with NTP-style `time:sync` probes (4 quick, then every 15 s, shortest round trip wins, `ClockSync`) and set `worldTime` every frame from the estimated server time, so clients with wrong clocks still agree. Offline (dev pages) the local clock still ticks.
- **Weather**: one schedule seed for every shard (`WORLD_WEATHER_SEED = 0`, my choice: the valley shares its sky and switching shards does not change it). The client takes the room's broadcast weather when online.
- **Remote avatars**: `scene/RemotePlayers.tsx` renders the other players in the same space from the room state (name, appearance JSON validated with `AvatarAppearanceSchema`, position, heading, motion) through snapshot interpolation drawn 120 ms in the past (`net/interpolation.ts`; cuts on teleports > 3 m or space changes, a move after a pause starts from rest). Each runs its own `AnimationStateMachine` from the synced motion plus relayed emotes. Emotes 1–5 (`EMOTE_KEYS`; `think` stays for M23) are sent only when the local machine accepts them; the server accepts them only while the player is idle, at most one per 0.6 s, and relays them to players in the same (non-private) space. A saved mirror edit is pushed to the player's TownRoom (`TownRegistry.applyProfile`), so everyone sees the new look.
- **Precision**: positions are synced with the schema `number` type, which encodes non-integers as 32-bit floats (≈ 8 µm at 100 m). Fine for rendering; the authoritative position is the server's float64 tracker.
- **Bundle**: the entry chunk grew 511.6 → 523 kB (the schema `Callbacks` decoder helpers and the session mirror; still no zod in it). Remote avatars are ~9 meshes each: a full 40-player shard in one place would far exceed the 150 draw-call budget. TODO(M37): distance culling / impostors / instancing for crowds.
- **Tests**: shared (clock mapping and `ClockSync`, `validateMove` with a walker running to the bakery, inside and back out, WASD wall slides, speed hacks, wall hops, doors, schemas), client (`MoveSync`, `RemoteTrack`, `getShards`), server multi-client tests with the real `@colyseus/sdk` in Node and a mocked verifier (two clients walk out of their apartments and see each other move and emote, speed-hack correction and epochs, wall/space rejections, 41 joins → shard 2, lowest-shard filling and join-a-friend by uid, one session per uid, clock sync + weather broadcast, mirror push), and a root test (`tests/town`) that runs the client's `townSession` mirror against a real server.
- **Not verified**: the acceptance check with two real browsers (no Firebase Auth emulator here, and no dev-only auth bypass was added on purpose); how smooth remote movement looks and feels on screen; remote avatar rendering in a browser (the code path only runs with a server connection).

- **Tokenized line schema** (shared `language/tokens.ts`): `TokenizedLineSchema` = `{text?, reading?, translation, tokens[1..80]}` with `TokenSchema` = `{surface, lemma?, reading?, romanized?, gloss (default ""), pos?}`, matching the NPC turn `lines[]` schema in npc-runtime.md (`reading` = kana for Japanese, pinyin / RR / transliteration otherwise; `romanized` = romaji for Japanese). Latin-script languages never show the toggle. Romanized mode maps CJK/Arabic punctuation to Latin and lays the line out LTR with `lang="xx-Latn"`.

- **Fonts (decision)**: Noto families per script (shared `language/fonts.ts`, all 25 scripts of the registry) loaded on demand from **Google Fonts** (`fonts.googleapis.com` CSS2 + `fonts.gstatic.com`, `display=swap`) by injecting one stylesheet link per family the first time a line in that script is shown. Why not self-hosted: Google serves CJK in unicode-range slices (a bubble downloads only its glyphs), while self-hosting (e.g. @fontsource) adds several MB of font files per CJK script to the Hosting deploy and more dependencies.
